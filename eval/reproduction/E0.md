# E0 baseline reproduction status

E0 has validated released code paths but has not yet produced a full “theirs /
reproduced” ASR-and-utility table. Published hosted-model numbers remain context,
not directly comparable measurements.

## Progent

Pin: `5be7b63fa96f70bc19b72fbcee81f1c0bcc1a565`.

The released `agentdojo/run.sh` selects `gpt-4o-2024-08-06` for both the acting
model and `SECAGENT_POLICY_MODEL`. Its core enforcement path is deterministic JSON
Schema validation in `secagent/tool.py`, with priority-ordered allow/forbid entries
and default deny for tools missing from the policy. E0 therefore has two separate
checks:

1. deterministic policy-semantic parity, which can run without a model; and
2. AgentDojo ASR/utility using the two pinned local Ollama models.

The second check is an artifact-local comparison and cannot be expected to match the
paper's hosted-model numbers. It must not be placed beside them as though the model
and transcript distributions were the same.

Completed: the released checker and `progent_style` agree on the fixed allow,
unknown-tool deny, and type-error deny corpus (3/3). The same released checker
approved all eight shared policy-conformant E2 calls; all eight below-boundary
canaries then landed.

## CaMeL

Pin: `f083b6b396399d3b3c7f2ddaf613a5945eaf32d8`.

The released model registry lists Google, Anthropic, and OpenAI models and rejects
other provider strings. The OpenAI client can be pointed at an OpenAI-compatible
base URL, but the model must also be added to CaMeL's supported-name map. The local
adapter will make only those two plumbing changes and will continue to execute the
released `main.py` and interpreter; it will not port CaMeL into our runner.

As with Progent, results from Qwen are not a reproduction of published closed-model
ASR. The valid E0 claims are runner fidelity, released policy replay behavior, and
within-artifact parity under the same local model.

Completed: the released test suite passes (126/126). A transient, recorded patch
adds only the two Ollama model names and OpenAI-compatible base URL plumbing. One
released workspace task completed with `qwen3:8b`, demonstrating the runner path;
utility was zero. That smoke run is excluded from E3 because the released runner
did not yet record the study seed and request-level audit metadata.

E2 also includes a deliberately narrow auxiliary case: a retrieved name carries a
trusted CaMeL source label, the released security-policy engine permits the call,
and our tool's post-check absolute-path join changes the resource actually opened.
This is not presented as a general break of CaMeL or as an exploit of its code. It
tests the stated structural limit: provenance mediation cannot confine a vulnerable
tool after an allowed call.

## Deployable bolt-ons

The released Eydii, Forge, and Nuggets integrations all intercept the tool call and
then invoke the handler after approval. E2 exercises those released wrappers with a
local approving authority because every shared trigger is policy-conformant. The
authority double is not a policy-engine reproduction and the result makes no claim
about vendor policy quality; it isolates mediation placement.

`langchain-forge==0.2.0` needs the explicit compatible transitive pin
`veritera==0.4.0`. Its declared `veritera>=0.2.0` resolves to 0.4.1 on the capture
date, which fails to import because `Forge` is no longer exported. Both the pin and
the resolution failure are recorded in `PINS.md`.

## Acceptance gate

E0 is complete only when:

- released unit tests pass at both pins;
- Progent's released policy checker and the `progent_style` slangGraph module agree
  on a fixed allow/forbid corpus;
- CaMeL runs its released AgentDojo path through the minimal local-model adapter;
- all runs use `configs/models.json` and write a hash-chained audit database; and
- the table labels published numbers as contextual, never directly comparable.

The first three gates are complete. Full audited model-run reproduction and the
comparative table remain pending.
